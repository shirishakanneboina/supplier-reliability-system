# Supplier Reliability System – Data Dictionary

## 1. Overview

This document describes the structure, data types, relationships, and validation rules for the 11 datasets generated by the Supplier Reliability System.

All datasets are synthetic and generated for project evaluation.

## 2. Entity Summary

| Entity | Records | Description |
|---|---:|---|
| Suppliers | 1,000 | Supplier master information |
| Sites | 1,976 | Supplier operating locations |
| Contracts | 2,016 | Supplier contract information |
| Purchase Orders | 10,000 | Orders placed with suppliers |
| PO Lines | 20,011 | Individual products and quantities in orders |
| Shipments | 15,000 | Shipment records linked to purchase orders |
| Delivery Events | 32,899 | Shipment tracking events |
| Inspections | 20,000 | Quality inspection results |
| Invoices | 10,000 | Supplier invoice information |
| Risk Signals | 1,514 | Supplier risk observations |
| Supplier Scores | 1,000 | Calculated supplier reliability scores |

## 3. Data Types and Conventions

- `str`: Text or identifier.
- `int64`: Whole number.
- `float64`: Decimal number.
- Date fields are stored as text and should follow `YYYY-MM-DD` format.
- Scores use a 0–100 scale.
- Required fields must not be null or empty.
- Primary keys must be unique.
- Foreign keys must reference existing parent records, except in isolated anomaly test cases.

|---|---|---|---|

## 6. Key Data Validation Rules

1. All primary keys must be unique and non-null.
2. Foreign keys must reference existing parent records.
3. Supplier references must remain consistent across related entities.
4. Contract end dates must not precede contract start dates.
5. Expected delivery dates must not precede order dates.
6. Shipment and delivery event dates must follow the shipment lifecycle.
7. Defective quantity must not exceed inspected quantity.
8. Defect rate must reconcile with inspection quantities.
9. PO line totals must reconcile with quantity multiplied by unit price.
10. Purchase order totals should reconcile with their PO lines.
11. Risk signals must contain a valid source and signal date.
12. Supplier performance scores must remain within the 0–100 range.
13. Score calculations must use only information available as of the scoring date.
14. Missing performance data must be distinguished from a genuine score of 100.

## 7. Anomaly Test Data

Deliberately invalid test cases are stored separately from the valid baseline datasets.

Files:
- `data/exports/anomaly_cases.csv`
- `data/exports/ground_truth.csv`

The anomaly scenarios cover:
- Shipment referencing a missing purchase order.
- Delivery occurring before dispatch.
- Future information used in a supplier score.
- Risk signal missing its source and date.
- Incorrect supplier-site association.

These isolated cases are intended for validation and expected-decision testing. They are not part of the normal relational baseline tables.

## 8. Data Provenance

All records are synthetically generated by the project's Python data generators. No real supplier or confidential business records are used.

The random seed and generation logic are maintained in the source code to support repeatable dataset generation.
